# PR、上线与恢复

## 准备与审核

记录 git status、当前分支、远端和 base SHA。存在用户未提交改动则用新的工作树，不重置、不顺手提交。拉取远端失败时，本地快照标明日期，不能声称已审核最新 main。审查准确的 PR diff 和实际 head SHA，按变更运行相关检查。代码审核不是只看 mergeable=true；没有 CI 要明确无 CI，不能称所有 CI 通过。

一个 PR 围绕一个有实际价值、可独立验证的问题；命名与内容一致。PR 描述使用 assets/pr-description.md。分支推送后创建 PR，再读取号码和链接，保留 head SHA。避免为了统计指标拆分无实际价值的 PR。

用户要求审核并合并时完成真实 diff 审核，修复阻碍，检查最新状态再合并。支持 expected head 时固定 SHA，防止期间被改。不能用同一作者账号虚构独立的批准审核；可说明自己做了代码检查。GitHub 连接器优先，不可用时使用已授权 CLI；浏览器作为后备。凭据用已有授权机制，不能打印 credential fill 输出。

## 发布

区分静态站部署、Worker 部署、数据库/存储迁移和 DNS 设置；仅推代码未必部署后端。读取项目实际流水线，记下部署 ID 与提交 SHA。查询已有任务结果，避免网络断开后重复触发。失败不无限循环，核实有无副作用后采取有界重试。

脚本辅助：`python <skill>/scripts/http_check.py https://example.com/path/ --contains "页面独有标题"`。检查 HTTP、标题文本不是完整验收；还应在浏览器检查导航、样式、资源、滚动和本次涉及的功能。认证测试用合适测试账号，勿在生产注销真实用户或制造交易。

## 回滚与交接

保留最后正常提交、发布目标、操作步骤。回滚源码通常用 revert 或重新部署旧版本；数据库恢复需单独评估并发新数据，不用旧 db.json 覆盖新内容。下线保留归档代码和恢复入口。最终说明已部署/仅 PR/待用户手动步骤，写出可访问地址和验证限制。

每周或逐日更新记录应读取 commit/PR 差异并按用户时区整理，区分提交时间与上线时间，不按记忆编造。
