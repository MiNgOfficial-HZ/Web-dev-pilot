# 从零开始：把想法变成可访问的网站

适用于用户没有仓库、没有本地代码，甚至还不知道网站需要哪些页面的情况。目标是陪用户完成实际网站，而非只交一份学习清单。

## 先把想法变成清楚的目标

先读对话、图片、参考链接和用户已经提供的资料，不让用户重复。缺少信息时，一次只问一个会影响方案的问题，例如“访客看完后最重要的动作是什么？”、“你想让所有人都能看，还是只给指定成员使用？”。用户不确定时，给一两个具体选项并说明推荐项；不要一开始连问技术栈、数据库、CI/CD、CDN等术语。

最少确认：

1. 网站服务谁、解决什么事？
2. 访客必须能完成哪一到三个动作？
3. 是否涉及登录、用户资料、上传、支付、预约或私密内容？
4. 用户有无现成域名、GitHub/代码托管账号、云平台账号、图片和品牌素材？未知项可以稍后再补。
5. 用户想先看本地效果，还是有权立即发布？

把答案写入 `assets/first-project-brief.md` 的副本，形成项目内 `docs/project-brief.md`。只记录有用决策、待确认项与验收方式，不写密码或密钥。用页面清单/简单草图与用户对齐，避免先堆代码再发现方向错误。

## 选择最省心的第一版方案

先用需求决定网站形态：

- 个人主页、作品集、公开文章、活动介绍：优先简单的静态或内容型站点，除非确实需要实时数据和账号。
- 有账号、权限、管理后台或持续写入的数据：选择能提供实际服务端和数据库的方案，并设计备份、权限和删除方式。
- 地图、互动可视化、小游戏：先做可独立打开的核心体验，再确定如何嵌入主站。
- 商店、收款、预约、邮件：先核对地区/账户资格/服务条款/回调能力；把真实服务端流程和人工开通步骤列出来。

依据当前维护状态、部署平台支持、用户已有技能或项目、长期成本和锁定风险选栈。给用户一句话解释“为什么这套适合你”。不要默认某个框架、数据库或组件库；用户已有平台或偏好时优先沿用。初始化生成器只负责脚手架，不代表视觉设计已经完成。页面设计遵循当前环境中适用的设计规范；风格从参考图、品牌和用途提取，不照抄无关示例。

## 从空目录创建项目

1. 选择工作区并确认最终目录名；盘点目标路径。只在新建空目录或明确授权的目录内写入，绝不清空非空目录来“重新开始”。
2. 为新项目初始化 Git；如连接 GitHub，使用用户已登录的官方 CLI/连接器。仓库公开性先设 private 或依用户明确选择。没有 GitHub 身份验证时，先完成本地项目和截图，标出登录这一步，不索取令牌。
3. 创建项目说明、页面骨架、全局风格、主要内容和必要交互。优先用项目原生组件。加上运行、构建、测试和部署说明；不要引入只为显得完整的复杂工具。
4. 先完成一个端到端可运行的第一版：安装依赖、开发预览、生产构建、关键路径检查、手机尺寸和直接打开子页面。使用明确的示例数据并标识待用户提供的正式内容。
5. 截图交付后处理托管。选项按现有栈和用户所在地可用性比较；用户没账号时引导他注册/登录提供者，尽量保持浏览器接管或官方 CLI 登录。部署密钥由用户在平台安全面板添加，不写入仓库、对话日志或截图。
6. 部署后验证线上首页、关键链接、移动布局、刷新/404、表单或服务端动作。配置域名前检查 DNS 现状；不要覆盖已有邮件 MX/SPF/DKIM 记录。域名证书与 DNS 生效需要实际查询验证。

## 常见人工步骤与续接

实名、商户签约、购买域名、组织授权、一次性验证码等必须由用户本人完成。先将可以独立完成的代码、预览和精确操作路径准备好，再告诉用户当前应该点击哪里、预期看到什么；用户返回后从保存的任务状态继续。不要把账号密码或私钥发给 AI。可以让用户在部署服务的 secret/settings 页面粘贴值，回来后只验证变量是否已配置，不回显值。

不同托管平台、免费额度、地区支持和账号政策会变化。选择服务前查官方当前文档与价格，清楚说明会不会收费、是否需要信用卡、网站是否公开；优先不用需要付费的默认设置。不能确认就先停在成本或地区资格选择点，给出证据并让用户决定。

## 新手常用词的说法

- 仓库：保存代码和历史修改的线上项目空间。
- 本地预览：只在自己电脑打开的临时网站。
- 部署/上线：把网站放到托管平台，让互联网能访问。
- 域名：网站的可读地址；DNS 是把域名指到服务的设置。
- 环境变量/密钥：服务器运行时用的私密配置，应在托管平台保管。
- PR：请求把一组代码改动合进主项目的审核记录；新建个人网站不一定需要 PR。

只在用户需要时解释一个词，不要把交付变成术语课。
